# 插件引擎横评：boa / QuickJS / V8（参考）

> 2026-10-21 执行，计划见 `docs/superpowers/plans/2026-10-22-engine-benchmark.md`。
> 原始数据：`tools/engine-bench/results/<commit>.json`（可复跑：`cd tools/engine-bench && cargo run --release -- run`）。

## 结论（先看这个）

1. **`3.2ms/帧` 是 debug 数字，release 下是 `0.125ms/帧`**（25 倍差）。boa 渲染 30×3 的
   picker 只占 60fps 预算的 **0.75%**。"每帧不能引 JS"作为**结构**判断仍然成立（多组件叠加、
   且渲染不是每帧唯一工作），但**不能再拿 3.2ms 当依据**。
2. **真正贵的是 JSON 与大批量字符串处理，不是渲染**：boa 解析一份 53KB 布局快照要
   **11.8ms**（阈值的 11.8 倍），比渲染贵 **95 倍**；5000 行 picker 过滤 7.1ms（阈值的 3.6 倍）。
3. **现在不该换引擎**。两个超标场景都能靠**改边界**消掉（见"改边界后的复测"），换引擎只是把
   11.8ms 变成 1.24ms —— 仍然是每帧预算的 7.4%，治不了根。
4. 若将来确实需要"插件里跑重活"：QuickJS 是 boa 的 **2.9–9.5 倍**，V8 是 **6–33 倍**
   （按场景），而 V8 的代价是 +80MB 二进制与 FFI 复杂度。
5. **改边界之后**（2026-10-21 当天完成）：picker 的 5000 行过滤从 7.3ms → **1.96ms**
   （新增 `helix.fuzzy.session/run/drop`，会话式）；`get_layout` 的 11.8ms **是伪问题**
   —— 真实布局快照只有 **312 字节**（见下）。

## 方法

| 项 | 值 |
|---|---|
| 机器 | AMD Ryzen 7 4800H（16 线程），Linux |
| 编译器 | rustc 1.91.0，`--release`（`opt-level=3` 默认，无 LTO） |
| 引擎 | boa 0.22（与产品同版本）· rquickjs 0.14（QuickJS，bundled C）· Node v24.20（V8，**参考上界**） |
| 协议 | 每场景 warmup 1 轮 + 5 轮取**中位数**；每轮 `iters` 次内层循环；计时在 Rust `Instant` / Node `hrtime.bigint` |
| 等价性 | 三个引擎跑**同一份** `scripts/*.js`，桩同名同 arity；每场景打印 checksum，**三引擎全部一致**（否则测的是桩） |

场景与判据（阈值沿用审计里的 0.5ms/帧、2ms/命令，另加 1µs/native、1ms/快照读、6ms/插件加载）：

| 场景 | 内容 | 对应真实负载 |
|---|---|---|
| `eval` | 执行一份 148 行的插件脚本（配置/工具函数/5 个命令/3 个事件/键位/状态栏） | 启动加载 17 个插件 |
| `filter` | 5000 行候选 → 子串过滤 → 排序 → 映射成行对象 | picker `items()` |
| `render` | 30 行 × 3 列 → 行对象 + 1 次样式查询（与 `bench_picker_frame` 同构） | immediate-mode 渲染 |
| `native` | 1000 次 `helix.get_style()` | JS→原生边界 |
| `json` | `JSON.parse` 一份 53KB 布局快照 | `helix.get_layout()` 读取 |

## 结果

| 场景 | 单位 | boa | quickjs | v8(node) | 阈值 | boa/阈值 |
|---|---|---|---|---|---|---|
| eval | ms/次 | **0.937** | 0.156 | 0.006 | ≤ 6 | 0.16× ✓ |
| filter | ms/次 | **7.135** | 2.456 | 0.629 | ≤ 2 | **3.6× ✗** |
| render | ms/帧 | **0.125** | 0.040 | 0.013 | ≤ 0.5 | 0.25× ✓ |
| native | µs/次 | **0.485** | 0.280 | 0.099¹ | ≤ 1 | 0.49× ✓ |
| json | ms/次 | **11.832** | 1.239 | 0.354 | ≤ 1 | **11.8× ✗** |

¹ Node 的 `native` 列测的是 **JS 函数调用**（V8 里桩就是 JS 函数），不是原生边界 ⇒ **不参与决策**。

`filter_core` 是**改边界后**的同一负载（见下节）：条目只搬一次，每次按键只传 query。

| 场景 | 单位 | boa | quickjs | 阈值 |
|---|---|---|---|---|
| filter（手写 JS 打分） | ms/次 | 7.346 | 2.389 | ≤ 2 |
| **filter_core（会话式，核心 nucleo）** | ms/次 | **1.957** | 1.629 | ≤ 2 ✓ |

校验值（三引擎一致，证明三个 harness 等价）：
`eval=20 · filter=55550 · render=6200 · native=13000 · json=50000`

### 单次成本复核（排除 GC 摊薄）

`json` 场景在 `--iters 1 / 10 / 100` 下分别是 **11.97 / 11.88 / 10.65 ms/次**
⇒ 这是**单次解析**的真实成本，不是累计 GC。

## 与旧数字的对照

| | 旧（`bench_picker_frame`，`cargo test` = debug） | 新（release，本文） | 倍数 |
|---|---|---|---|
| render 30×3 | ≈3.2 ms/帧 | **0.125 ms/帧** | 25× |

结论修正：`docs/plugin-vs-core.md` 里"每帧 JS 渲染 = 预算 19.2%"应改为 **0.75%**；
该文档的 G1 判据（每帧路径不引 JS）依然成立，但**理由要换**：不是"太贵"，而是
"多个组件叠加 + 帧预算里还有布局/绘制/语法高亮"，以及"渲染逻辑一旦在 JS 里，核心就再也
没法保证不变量"（G2）。

## 为什么现在不换引擎

按计划的三段论，boa 在 filter/json 两个场景超阈值 2 倍以上 ⇒ 需要给"换引擎的代价与收益"：

| | 换 QuickJS（rquickjs） | 换 V8（deno_core） |
|---|---|---|
| filter / json 收益 | 2.9× / 9.5× | 11× / 33× |
| 换完是否达标 | filter 2.46ms（仍超 2ms）· json 1.24ms（仍超 1ms） | 达标 |
| 构建代价 | +C 工具链（bundled quickjs），`unsafe` FFI 面 | 二进制 +80MB，构建时间显著上升 |
| 风险 | 崩溃/UB 从 Rust 挪到 C；调试要靠 C 栈 | 生态绑定、跨平台构建矩阵 |

**关键点：换引擎后 filter/json 依然贴着阈值**，说明这两个场景的问题**不在解释器**，
在"把 5 万行/53KB 交给 JS 逐条处理"这个设计。换引擎等于花大代价把 3.6× 压到 1.2×，
下一次数据量翻倍就又超了。

## 改边界后的复测（2026-10-21 当天做的两件事）

### ① picker 的大列表过滤 → 核心 `helix.fuzzy`（会话式）

新增 `helix.fuzzy.session(items)` / `run(id, query, opts)` / `drop(id)`，`picker-ui` 在
`all.length >= core_match_min`（默认 1000）时切过去。**7.35ms → 1.96ms（3.75×）**，进入阈值。

这条路踩了两个坑，都是量出来才发现的，记在这里防止下次重犯：

| 形状 | 5000 条 / 次 | 结论 |
|---|---|---|
| 手写 JS 打分（旧） | 7.35 ms | 基线 |
| `filter(query, items)` **一次性** | **11.0 ms** | **比 JS 还慢**：5000 个字符串逐项过边界，搬运成本 > 打分 |
| `session` + `run`，但每次 `run` **克隆**条目 | ~2.2 ms | 克隆 5000 个 String 本身就是 0.2ms 量级 |
| `session` + `run`（借用，不克隆） | **1.96 ms** | 其中 nucleo 打分 ~1.4ms（5000 条 × 286ns） |

**教训：把工作搬进核心时，主成本是"每次调用跨越边界的数据量"，不是算法。**
句柄/会话的本质就是把 O(条目数) 的搬运挪到 O(1) 次。

### ② 布局快照的 JSON 往返 → **伪问题，已撤回**

上一轮我按"53KB 快照 parse 11.8ms"提出"布局快照别走 JSON"。实测真实快照：

- 2 叶布局的 `layout.dump()` 序列化 = **312 字节**（`sync_layout_cache` 里打印实测）；
- 按 boa 的 4.5 MB/s 解析速率 ⇒ **约 0.07 ms**，可以忽略；
- 全仓**没有任何内置插件调用** `helix.get_layout()`（`grep` 为空），第三方插件才用。

所以这一条**不改代码**，改成文档约束：`get_layout()` 的成本 ≈ `字节数 / 4.5MB/s`，
**超过 ~5KB 才会开始占用 1ms 以上**；需要局部信息时优先用 `helix.pane.list()`（已拍平的轻量视图）。

### ③ 仍然建议做的

- `get_layout()` 的文档补一行成本公式（上面那条）。
- 把本次的阈值写进 `cargo xtask` 守卫（`bench-check`），防止下次有人把 5 万行塞进 `items()`。

## 未测 / 局限

- **wasm（wasmtime）未测**：触发条件是 boa 与 quickjs 差距 < 2×，实测 2.9–9.5× ⇒ 不触发。
- **Node 的 native 列不可比**（见上）。
- 只测了**单线程**主路径；`helix.run_async` 那类 worker 负载不在引擎成本里。
- 场景数据是合成的（5000 行 / 53KB / 30 行）；真实 picker 的行宽与样式数量会有出入，
  但数量级不会变（json 的成本与数据量线性）。
