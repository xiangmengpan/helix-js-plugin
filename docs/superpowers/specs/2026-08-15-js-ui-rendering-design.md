# 设计:JS 组件视图层(Rust 底层服务 + JS 渲染)

日期:2026-08-15
状态:草案(未执行)
关联:docs/handoff-2026-08-14.md、specs/2026-08-14-window-mode-design.md

## 1. 背景与动机

用户对终端架构的疑问:terminal/filetree 等组件"是插件还是核心功能"?
当前答案:**混合架构**——组件渲染/状态机在 Rust(PluginTerminal、PluginPanel),JS 只提供命令入口与钩子。

用户的真实意图:**Rust 提供底层 UI 与会话行为(pty、布局、事件、绘制原语),组件渲染由 JS 完成**。
即插件(JS)是组件的"视图层",Rust 是"服务层"。这与 zellij 的插件化 UI、Neovim 的 UI 外置(lua 侧渲染)同构。

本文档定义该演进的分层边界、API 草案、迁移路线,不执行。

## 2. 现状盘点

### 2.1 已经是"Rust 底层 + JS 视图"的部分

| 组件 | Rust(底层) | JS(视图) | 每帧 JS 回调 |
|---|---|---|---|
| popup | 层管理、绘制、事件路由 | `render` 回调返回 `el` 字符/样式数组 | ✅ |
| filetree / panel | 面板容器、输入分发 | `open_panel` 的 `render` 回调返回行 | ✅ |
| statusline | 分段绘制 | `set_statusline` 返回分段数组 | ✅ |
| bufferline(经 set_buffer_icon) | gutter 图标绘制 | 图标映射回调 | ✅ |

这些组件的模式:**JS 生成绘制内容(字符+样式),Rust 执行绘制**。已验证可行且性能可接受。

### 2.2 缺口:终端

| 层 | 现状 |
|---|---|
| pty、escape 解析、网格、滚动、光标 | Rust(PluginTerminal) |
| Insert/Normal 模式状态机、按键行为 | Rust(刚硬化:Esc→normal 等) |
| 视图(标题、最小化条、边框、样式) | Rust 写死 |
| JS 参与 | 命令入口 + 8 个钩子(通知/单键决策) |

终端是唯一"JS 视图零参与"的组件。

## 3. 目标架构

```
┌─────────────────────────────────────────────┐
│ JS 视图层(插件)                              │
│  · 组件外观(标题/装饰/样式/布局偏好)          │
│  · 交互映射(点击区域 → 动作)                 │
│  · 状态展示(从会话 API 读,经渲染指令画)       │
├─────────────────────────────────────────────┤
│ 视图 API(会话 ↔ 插件)                       │
│  · render_instructions(组件 → 指令数组)      │
│  · get_component_state(组件状态只读)         │
│  · on_component_event(交互/生命周期通知)     │
├─────────────────────────────────────────────┤
│ Rust 服务层(核心)                            │
│  · pty、escape 解析、网格数据                │
│  · 布局树、焦点、模式状态机                  │
│  · 绘制原语(文本/样式写 surface)             │
│  · 输入事件路由、按键策略                    │
└─────────────────────────────────────────────┘
```

原则:
- **Rust 拥有数据与性能路径**,JS 拥有外观与交互决策
- 渲染指令是**声明式绘制意图**,不是像素/网格数据
- 每帧 JS 回调限于组件数(个位数),不随网格大小增长

## 4. 性能边界(为什么终端网格不能全 JS)

终端网格是高频大体积数据:pty 输出 → escape 解析 → 80×24+ 格更新,每帧可能全量变化。
若 escape 解析与网格构造在 JS(boa 解释执行):
- 每字节/每块 JS 回调:pty 高吞吐时 JS 成为瓶颈(解释器 ~10-100x 慢于原生)
- 每帧网格数据跨边界传递:数千格 × 字符+样式,序列化成本不可接受

**结论**:escape 解析与网格渲染必须留在 Rust。JS 可获得的终端视图数据是**汇总/装饰级**(标题、模式、滚动偏移、最小化状态、边框样式),非逐格数据。

## 5. API 设计草案

### 5.1 渲染指令(通用化 popup 的 `el` 机制)

```js
// JS 侧返回的绘制指令(数组)
// 类型:文本 / 填充 / 边框
{
  text: "─ terminal ─", style: "ui.popup", x: 0, y: 0,           // 文本
  fill: " ", style: "ui.background", x: 0, y: 0, w: 20, h: 1,     // 填充
  border: { style: "ui.popup", x: 0, y: 0, w: 20, h: 10 },        // 边框
}
```

- `helix.render_instructions(componentId, () => [...] )`:注册组件视图回调
- Rust 每帧调用,按指令写 surface(与现 popup/statusline 同路径)
- 指令裁剪/坐标由 Rust 处理,JS 只给逻辑坐标

### 5.2 组件状态只读 API

```js
helix.get_component_state(componentId)
// 终端:{ mode:"insert"|"normal", minimized, zoomed, title, scrollOffset, hasScrollback }
// 面板:{ side, size, entries? }  // entries 已在 JS 侧(filetree 自己持有)
```

- Rust 提供**汇总状态**(组件内部数据已由 Rust 拥有,如终端网格/模式)
- JS 视图据此决定画什么(标题条、最小化条、模式指示)

### 5.3 交互反馈

```js
helix.on("component-event", (componentId, { kind:"click"|"scroll"|"hover", x, y }) => ...)
```

- 鼠标命中(现 P4)只提供"区域 + 坐标",不解析组件内部
- JS 决定:点最小化条 → 调 layout_minimize;点标题 → 聚焦;滚动 → 调 scroll API

### 5.4 会话行为 API(已有,补齐)

现有布局/终端/面板 API 即"会话行为"层,保持。新增:
- 终端:滚动偏移读写(scroll_offset 现为 Rust 私有)、标题设置
- 面板:渲染指令注册(替代 render 字符串回调,向后兼容)

## 6. 组件迁移路线图

### 阶段 A:通用渲染指令 API(基础设施)

- `render_instructions` 注册 + Rust 执行器(指令→surface)
- 迁移 popup/statusline 到指令模型(或并存,旧回调保持)
- 交付物:指令 API + 示例插件画一个自定义弹窗
- 验证:集成测试断言 surface 内容;现有 popup/statusline 测试不回归

### 阶段 B:终端视图 JS 化(壳,非网格)

- 终端最小化条、标题栏、边框、模式指示 → JS 用指令绘制
- 网格本体留 Rust(性能)
- `get_component_state` 暴露终端的标题/模式/滚动状态
- 交互:点击标题聚焦、点击最小化条最小化(经 component-event)
- 交付物:terminal.js 渲染终端外观;Rust 默认外观作为无插件兜底

### 阶段 C:面板深化 + 新组件

- filetree 迁移到指令模型(现为字符串行,升级为带样式指令)
- 布局标签条(二期窗口模式候选)作为 JS 组件示范
- 组件状态 API 扩展(按需)

### 阶段 D(可选,不做承诺):行为策略插件化

- 组件按键策略(如 Esc→normal)从 Rust 硬编码改为"Rust 默认 + JS/Rust 插件覆盖"
- 依赖阶段 A 的事件反馈机制,评估后决定是否实施

## 7. 每阶段验证

- 阶段 A:helix-js lib 单测(指令→surface 映射)+ 集成(插件画自定义 UI)
- 阶段 B:渲染断言(终端外观含 JS 绘制的标题/最小化条)+ 现有终端行为测试全绿
- 阶段 C:filetree 样式测试;标签条渲染测试
- 全量:每阶段末全量集成回归(约 244 项)+ clippy

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| 每帧 JS 回调叠加性能 | 指令只覆盖视图层(个位数组件);网格/解析永不进 JS;基准测量每阶段 |
| 指令 API 与现有回调并存混乱 | 阶段 A 先统一 popup/statusline;旧回调短期兼容,文档标记 deprecated |
| 终端外观 JS 化后无插件时退化 | Rust 保留默认外观(无注册回调 → 内建绘制) |
| 交互(鼠标)复杂度 | component-event 只给区域坐标;命中解析留 JS,分期(P4) |

回退策略:每阶段独立可回退——指令 API 是新增层,不删除现有路径;阶段 B 的 Rust 默认外观保证无 JS 时行为不变。

## 9. 与现有系统的关系

- 布局树、窗口模式、终端钩子(term-*)保持不动
- 新 API 是**增量**:渲染指令与 get_component_state 是视图层的读/画通道,不改 Rust 服务层内部
- JS 钩子(通知/单键)与视图回调并存:钩子管行为通知,视图回调管外观

## 10. 规模评估

- 阶段 A:中(指令模型 + 执行器 + 迁移,约 1 个任务)
- 阶段 B:中(终端状态暴露 + 外观指令化 + 默认兜底,约 2 个任务)
- 阶段 C:中(迁移 + 标签条新组件,约 2 个任务)
- 总计约 5 个任务,均可独立交付
